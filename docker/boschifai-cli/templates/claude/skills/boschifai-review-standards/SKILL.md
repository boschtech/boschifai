# Boschifai Review Standards

These standards are **binding** for all requirement testability reviews generated by Boschifai. They define how to score, categorize, and report findings consistently across projects.

## Testability Scoring

Score = (Testable requirements / Total requirements) x 100

| Score | Rating | Action |
|-------|--------|--------|
| 80-100% | Green | Proceed to test design |
| 60-79% | Yellow | Resolve blockers before full test design; partial design can start |
| 0-59% | Red | Block test design; return to requirements refinement |

## Finding Severity Definitions

| Severity | Definition | Impact on Testing |
|----------|-----------|-------------------|
| **High** | Blocks test design or execution entirely | Cannot write deterministic pass/fail test |
| **Medium** | Creates ambiguity that will cause rework or defect leakage | Test can be written but may be non-deterministic |
| **Low** | Cosmetic or classification improvement | Test is possible but could be clearer |

## Finding Categories

- Missing NFRs
- Untestable AC
- Ambiguous AC
- Missing AC
- Contradictory AC
- Missing specification
- AC classification (process vs. functional mixed)

## Acceptance Criteria Quality Dimensions

Rate each AC on these dimensions:

| Dimension | Yes | Partial | No |
|-----------|-----|---------|-----|
| **Clear** | Unambiguous language, no undefined terms | Some ambiguity | Major undefined terms |
| **Complete** | All states/paths covered | Some gaps | Major gaps |
| **Testable** | Deterministic pass/fail possible | Requires assumptions | Cannot test |
| **Atomic** | One assertion per AC | Slightly compound | Heavily compound |

## Mandatory Report Sections

Every testability review MUST contain:
1. Header with score and blocked count
2. Requirement summary (brief)
3. Testability assessment table
4. Acceptance criteria testability table with Given/When/Then rewrites
5. Missing test requirements (numbered gaps)
6. Test preconditions and dependencies
7. Risk-based testing priorities
8. Clarifying questions for test design

## Given/When/Then Rewrite Rules

When rewriting non-testable ACs:
- **Given** = precondition (state before action)
- **When** = trigger (single user/system action)
- **Then** = observable outcome (measurable, verifiable)
- Use **And** for additional assertions (one per line)
- Never use subjective terms: "appropriate", "reasonable", "minor", "acceptable"
- Always include exact values where thresholds exist
