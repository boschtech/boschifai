# Boschifai Test Patterns

These patterns are **binding** for all test lifecycle artifacts generated by Boschifai prompts and commands. They define how tests are structured, named, and organized across projects.

## Test Case ID Convention

Format: `TC-<SOURCE>-<SEQ>`

- `<SOURCE>` = Jira key (e.g., RIBE-24955) or requirement ID (e.g., REQ-001)
- `<SEQ>` = 2-digit sequence number, zero-padded

Examples: `TC-RIBE-24955-01`, `TC-REQ-001-03`

## Test Case Structure (mandatory)

Every test case MUST include:

| Field | Required | Notes |
|-------|----------|-------|
| Priority | Yes | Critical / High / Medium / Low |
| Type | Yes | Functional / Negative / Boundary / Security / Performance / Accessibility |
| Requirement | Yes | Traceable back to source |
| AC | Yes | Which acceptance criterion |
| Automatable | Yes | Yes / No / Partial |
| Test Data | Yes | Exact values, never placeholders |
| Preconditions | Yes | What must be true before execution |
| Steps | Yes | Action + Expected Result per step |
| Postconditions | Yes | State after completion |

## Coverage Techniques (apply systematically)

1. **Equivalence Partitioning** — identify valid/invalid input classes
2. **Boundary Value Analysis** — test at min, min+1, max-1, max, max+1
3. **State Transition** — test all valid transitions and invalid ones
4. **Decision Table** — for multi-condition business rules
5. **Error Guessing** — null, empty, special chars, injection, XSS
6. **Pairwise** — for multiple interacting parameters

## Test Ordering Within a Requirement

1. Happy path first
2. Alternate valid paths
3. Negative / boundary
4. Error handling
5. Edge cases

## Naming Convention for Generated Files

| Artifact | File Name Pattern |
|----------|-------------------|
| Testability Review | `testability_review_<JIRA_KEY_or_NAME>.md` |
| Test Strategy | `test_strategy_<NAME>.md` |
| Test Plan | `test_plan_<NAME>.md` |
| Test Cases | `test_cases_<JIRA_KEY_or_NAME>.md` |
| API Tests | `api_tests_<NAME>.md` |
| Test Data | `test_data_<NAME>.md` |
| Traceability Matrix | `traceability_matrix_<NAME>.md` |
| Defect Report | `defect_report_<NAME>.md` |
| Test Execution Report | `test_execution_report_<NAME>.md` |

## Quality Rules (non-negotiable)

1. **Specific actions** — never "enter valid data"; specify exact input
2. **Observable results** — every expected result must be verifiable
3. **Independent** — each TC executable standalone
4. **One assertion per step** — don't bundle validations
5. **Repeatable** — same input always produces same output
6. **Traceable** — every TC links to requirement and AC
7. **Test data specified** — exact values, not "valid email"
