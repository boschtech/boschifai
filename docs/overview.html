Boschifai

Boschifai takes a plain-text requirement and turns it into a GitHub pull request that contains working automated tests. Claude Code analyses the requirement, plans and writes the tests, and runs them for real against the target repository. A person approves the work at two points along the way. Once CI finishes, Boschifai reports a composite confidence score.

Connect a repository with GitHub OAuth, or point Boschifai at a repo already checked out on disk. Each connected repo gets one persistent checkout that every run shares, so only one run per repo can be in flight at a time.

How a run flows

From requirement to pull request

Every stage runs as a queued Laravel job, and each job chains the next one automatically. Only the two gates need a person. app/Enums/RunState.php holds the authoritative state machine.

  1. Gap analysis

    /boschifai-review

    Scores the requirement's testability and lists its gaps. In coverage mode, this stage writes a codebase knowledge base instead.

    gap_analysis_running

  2. Test plan

    /boschifai-test-plan

    Writes the test plan. Coverage runs also choose their own target file, extracted from a RECOMMENDED_TARGET_FILE: line.

    gap_analysis_ready

  3. Gate 1: approve the analysis and plan

    A reviewer approves or rejects the combined review and plan. Rejecting ends the run as gap_analysis_rejected.

  4. Test case generation

    /boschifai-test-cases

    Produces test cases and checks them with a built-in validator. A NEEDS_FIXES verdict triggers up to 2 automatic retries before the run blocks for a person.

    generation_running → generation_blocked?

  5. Code generation

    /boschifai-gen-component

    Writes the test file straight into the shared checkout. Requirement runs produce a PHPUnit Feature test. Coverage runs use whatever framework the target repo already has.

    generation_running

  6. Local execution

    test-runner sidecar

    Runs the generated tests for real in an isolated container and parses the JUnit results. Fix failing tests asks Claude to edit the file in place, then re-runs this stage.

    local_execution_running → local_execution_complete

  7. Gate 2: approve the code and real test results

    The reviewer sees the generated code, the pass/fail results and a pre-push confidence score. Rejecting ends the run as push_rejected.

  8. Push and open PR

    git + GitHub REST

    Creates a branch, commits exactly the generated file (never git add -A, and this is enforced) and opens a pull request. When GITHUB_MCP_PAT is set, a tightly limited Claude session with the GitHub MCP server handles this step instead.

    pushing

  9. CI polling and report

    every 30 s, up to 30 min

    Watches the target repo's existing sonar-scan.yml check run without changing any workflow files, then calculates the final confidence score.

    ci_pending → ci_complete → report_ready
Run types

Four ways to start a run

requirement

Requirement

You write a requirement and name a target file. The run goes through the full pipeline and both gates, and ends with a PHPUnit Feature test in a PR.

coverage

Coverage

You give an instruction like "increase coverage for X". The pipeline chooses the target file and records an execution recipe for the repo's own test stack.

build_skills

Build Skills

A standalone action: one Claude invocation scans the repo and fills in a project-specific skill template. There are no gates and no push.

build_knowledge_base

Build Knowledge Base

A standalone action that writes a codebase knowledge base for the repo. It is stored as a run, so it appears in history and reporting.

Architecture

Four containers and one hard security boundary

app

Serves the Vue SPA and the JSON API using php -S with router.php. It never runs a job and never modifies a checkout. Local repos are mounted read-only here, for browsing.

worker

Runs queue:work. It prepares the checkout, runs boschifai init, drives headless Claude Code, commits, pushes and polls CI.

test-runner

Runs the connected repo's own composer install and test command. It has no .env, no DB_* variables and no API key.

db

MySQL 8. It stores runs, steps, Claude invocations, artifacts, approvals and results. It also backs the job queue.

Why the test-runner is isolated

This split comes from a real incident. A connected repo's test suite inherited the worker's live database credentials, and its RefreshDatabase trait ran migrate:fresh against Boschifai's own database. The test-runner now has no way to reach that database, whatever the tests try to do.

Reporting

Composite confidence score

Four signals, each scored 0 to 100, are combined using weights from config/boschifai.php. CI has the highest weight because it is the only fully independent signal. The weights are a starting proposal for the team to tune.

Status

Known gaps

These are open TODOs. The code paths that depend on them fail with a clear error.

  • No authenticationNothing protects /api/*. The local-repo browser is confined to one root directory as a partial safeguard.
  • Claude isn't sandboxedclaude runs inside the worker with its database and queue credentials. Production needs a locked-down container that can only reach api.anthropic.com.
  • Secrets in .envThe Anthropic key, OAuth secret and MCP PAT should come from AWS SSM in production.
  • Revoked GitHub access goes unnoticedThere's no webhook receiver, so a revoked token is only discovered the next time Boschifai tries to use it.
  • One run per repoRuns share one checkout per repo, so a second concurrent run is rejected rather than queued.
  • Cost ceiling and tool importsmax_cost_per_run_usd has no agreed figure and isn't enforced yet. Importing requirements from Jira or Monday.com is a placeholder.
